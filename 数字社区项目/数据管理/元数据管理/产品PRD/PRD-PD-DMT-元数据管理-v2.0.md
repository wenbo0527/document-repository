## 三、需求背景

### 3.1 目标

元数据管理系统提供企业级元数据的统一建模、采集、存储与检索能力，支持数据资产、要素、资源的上下架管理，构建完整的元数据资产视图。

### 3.2 痛点

1. **元数据分散**：各系统元数据散落，缺乏统一建模和管理入口
2. **采集成本高**：元数据采集依赖人工维护，成本高且容易遗漏
3. **上下架混乱**：资产、要素、资源缺乏统一的上下架管理机制
4. **标签缺失**：元数据缺乏标签体系，检索和分类困难

### 3.3 核心挑战

1. 多源异构元数据的自动采集与标准化
2. 上下架审批流程与数据资产联动
3. 标签体系的灵活扩展与继承

**Story META-001：创建元数据模型**

| 字段 | 内容 |
|:---|:---|
| 角色-场景-价值 | 作为数据架构师，需要创建新的元数据模型，定义模型名称、字段结构、数据类型，以便后续数据资产能够挂接该模型 |
| 优先级 | P0 |
| 状态 | 待开发 |

**验收标准**：

1. 支持新建模型，填写模型名称、模型类型（业务模型/技术模型）、描述
2. 支持添加字段：字段名、字段类型、是否必填、默认值、注释
3. 支持字段拖拽排序
4. 模型保存前进行必填校验，未填写完整禁止保存
5. 保存成功后提示「模型创建成功」，自动跳转模型详情页

**交互说明**：

模型列表页点击「新建模型」按钮；弹出模型创建表单Dialog；字段列表支持动态添加行；字段类型下拉可选（STRING/INT/BIGINT/DECIMAL/DATE/DATETIME/JSON/ARRAY）；点击「保存」触发表单校验；校验失败在对应字段下方展示错误提示。

**Story META-002：编辑元数据模型**

| 字段 | 内容 |
|:---|:---|
| 角色-场景-价值 | 作为数据架构师，需要编辑已有元数据模型的字段结构或属性，保持模型与实际数据源结构一致 |
| 优先级 | P0 |
| 状态 | 待开发 |

**验收标准**：

1. 打开已有模型，进入编辑模式后可修改模型名称、描述、字段结构
2. 支持增加、删除、修改字段
3. 支持修改字段类型，修改时提示「字段类型变更可能导致数据丢失」
4. 保存前进行必填校验
5. 编辑操作记录操作日志，包含操作人、操作时间、变更内容

**交互说明**：

模型详情页右上角「编辑」按钮；进入编辑模式后所有字段变为可编辑状态；删除字段时弹出确认Dialog「删除字段将同时删除该模型下所有资产的该字段数据，确认删除？」；保存成功后退出编辑模式，页面刷新为最新数据。

|:---|:---|
| 角色-场景-价值 | 作为数据架构师，需要查看元数据模型的历史版本，对比不同版本之间的差异，并在必要时回滚到旧版本 |
| 优先级 | P0 |
| 状态 | 待开发 |

| 角色-场景-价值 | 作为数据架构师，模型设计完成后提交发布申请，审批通过后模型正式生效，可被数据资产引用 |
