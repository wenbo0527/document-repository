## 2. 需求拆解流程

### 2.1 流程图

```
业务需求输入
    │
    ▼
┌─────────────────┐
│  需求理解       │  ← 输入：原始需求
│  ProductContext │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  产品分析       │  ← 分析影响范围、风险
│  ProductAnalysis│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  PRD 生成       │  ← 输出：Epic/Feature/Story
│  PRDGenerator   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  人工审核       │  ← PM 审核确认
│  Human Review   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  同步到 Neo4j   │  ← 状态更新
│  DataSync       │
└─────────────────┘
```

### 2.2 流程说明

| 步骤 | 操作 | 负责人 | 输出 |
|:---:|:---|:---|:---|
| 1 | 收集业务需求 | 产品经理 | 原始需求文档 |
| 2 | 需求理解 Agent 分析 | AI Agent | 结构化需求 |
| 3 | 产品分析 Agent 评估 | AI Agent | 影响分析报告 |
| 4 | PRD 生成 Agent 拆解 | AI Agent | Epic/Feature/Story |
| 5 | 产品经理审核 | PM | 审核意见 |
| 6 | 根据意见修改 | AI Agent | 修改后文档 |
| 7 | 确认并同步 | PM | 最终文档 |
| 8 | 同步到 Neo4j | DataSync Agent | 图数据库更新 |

## 6. 数据同步流程

### 6.1 触发条件

| 触发类型 | 说明 |
|:---|:---|
| 自动同步 | 状态变更时自动同步 |
| 手动同步 | 用户主动触发 |
| 定时同步 | 每日凌晨全量同步 |

### 6.2 同步优先级

| 优先级 | 说明 | 超时时间 |
|:---|:---|:---:|
| P0 | 紧急同步 | 1 分钟 |
| P1 | 正常同步 | 5 分钟 |
| P2 | 低优先级 | 30 分钟 |

### 6.3 异常处理

| 异常 | 处理方式 |
|:---|:---|
| Neo4j 连接失败 | 重试 3 次，间隔 10 秒 |
| 飞书 API 限流 | 加入队列，延迟处理 |
| 数据不一致 | 记录日志，告警通知 |

## 7. Epic Feature 文档重建 SOP（新增 v1.1）

> **来源**: 2026-04-27 数字营销重建实践经验
> **适用场景**: 初始化 Epic、修复文档质量问题、PRD 更新后同步

### 7.1 重建触发条件

| 触发条件 | 说明 | 优先级 |
|:---|:---|:---:|
| 新 Epic 创建 | 首次建立 Epic 文档体系 | P0 |
| PRD 重大更新 | Feature/FP 数量或内容变化 | P1 |
| 文档质量检查不合格 | FP 内容为占位符、README 与实际不符 | P0 |
| 钟离提供技术规范 | 技术方案更新后需同步 README | P1 |

### 7.2 重建标准流程

```
Step 1: 读取源数据
    ├── 读取 Epic README.md（当前状态）
    ├── 读取 Epic PRD（Feature/FP 清单）
    └── 读取 Neo4j（验证 Epic/Feature 关联）

Step 2: 目录结构检查
    ├── 确认 Epic 下 5 个标准子目录存在
    ├── 确认每个 Feature 目录下有 3 个标准子目录
    └── 清理技术方案下的旧 Feature 残留目录

Step 3: Feature 命名与 ID 核对
    ├── README Feature 表格 vs 实际目录数量
    ├── 哈希格式 ID 处理：功能存在→保留，功能已迁移→删除
    └── 缺失目录：新建标准目录 + 初始化文档

Step 4: FP 内容重建
    ├── 解析 PRD 中 FP 表格（ID、名称、功能描述、验收标准）
    ├── 分配 FP 到对应 Feature（PRD Feature → 实际目录映射）
    └── 扩展验收标准为四项（功能/操作/数据/交互）

Step 5: README 同步
    ├── Feature 表格数量对齐实际目录
    ├── 删除哈希格式残留（如已迁移）
    ├── 版本号 +0.1，补充变更记录
    └── 菜单结构对齐钟离理想（如提供）

Step 6: Neo4j 同步
    └── 确认 Epic→Feature→FP 关联关系与文档一致
```

### 7.3 Feature 目录结构规范

**Epic 目录结构（5 个标准子目录）**：
```
Epic/
├── README.md                    ✅
├── 业务需求入口/                 ✅ (仅有 .md 文件)
├── 产品PRD/                     ✅
├── 产品操作手册/                 ✅
├── 技术方案/                     ✅ (仅有 .md 文件)
└── 需求拆解结果/
    └── Feature/
        └── FEAT-xxx/
            ├── Feature说明文档.md  ✅
            ├── FP/                  ✅ (可空目录)
            └── 业务需求入口/        ✅ (可空目录)
```

**每个 Feature 必须包含的文件**：
- `Feature说明文档.md`（含 ## 1. 基本信息 + ## 2. FP 清单 + ## 3. 变更记录）

### 7.4 FP 内容重建规范

**FP 验收标准四项模板**：

| 验收项 | 填写规则 | 示例 |
|:---|:---|:---|
| 功能验收 | 描述功能正常工作的标准 | 渠道配置保存成功，状态管理正常 |
| 操作验收 | 描述操作响应时间/体验 | 配置保存<1s，表单校验提示清晰 |
| 数据验收 | 描述数据准确性和一致性 | 配置数据正确存储，与数据库一致 |
| 交互验收 | 描述用户交互体验 | 配置面板布局规范，错误提示准确 |

**FP ID 命名规范**：`FP-{Epic前缀}-{Feature后缀}-{序号}`

**版本号规范**：每次 FP 重建 +0.1（如 v3.0 → v3.1）

### 7.5 哈希格式 Feature ID 处理原则

**定义**：哈希格式指 `FEAT-xxx-XXXX`（4 位哈希后缀），多为旧版本迁移残留。

**处理决策树**：

```
发现哈希格式 Feature 目录
    │
    ├── 功能是否仍在使用？ ──否──→ 删除目录
    │       │
    │      是
    │       │
    ├── 是否有对应的标准 ID 目录？ ──是──→ 保留哈希格式（合法存量）
    │       │
    │      否
    │       │
    ├── 功能是否在钟离规范中？ ──是──→ 重命名为标准 ID
    │       │
    │      否
    │       │
    └── 询问文博确认
```

**经验规则**：
- 哈希格式目录**实际存在且有功能** → 合法存量，保留
- 哈希格式目录**只存在于 README 表格但目录已删除** → 残留，清理
- 标准 ID 命名格式：`FEAT-{产品前缀}-{模块后缀}-{序号}`（如 `FEAT-MKT-BENEFIT-01`）

### 7.6 重建质量检查清单

| # | 检查项 | 方法 |
|:---:|:---|:---|
| 1 | Feature 目录数量 = README 表格数量 | `ls Feature/ | wc -l` vs `grep -c "FEAT-" README` |
| 2 | 所有 Feature 有 Feature说明文档.md | `find Feature -name "Feature说明文档.md" | wc -l` |
| 3 | 所有 Feature 有标准子目录 | `find Feature -mindepth 1 -maxdepth 1 -type d` |
| 4 | FP 功能描述不为"正常"占位符 | `grep "功能描述.*正常" Feature说明文档.md`（应无结果）|
| 5 | FP 验收标准四项完整 | 检查每个 FP 四个验收项 |
| 6 | README 无哈希格式残留 | `grep "FEAT-.*-[0-9A-F]\{4\}" README`（应无或仅合法存量）|
| 7 | 版本号已更新 | `grep "版本" README.md` |

### 7.7 并行处理策略

**大规模重建（Epic 含 10+ Feature）时**：

| 策略 | 适用场景 |
|:---|:---|
| subagent 并行 | 多个 Epic 并行处理，每个 Epic 一个 subagent |
| 主 agent 处理 | 单 Epic 内逻辑复杂、需精确控制的部分（如营销画布）|
| Python 脚本 | 大量重复性子任务（如批量替换 FP 内容）|

**subagent 超时处理**：
- subagent 超时后检查文件内容（版本号/FP 是否已写入）
- 实际已写入 → 无需处理
- 未写入 → 主 agent 补做或写 Python 脚本处理
