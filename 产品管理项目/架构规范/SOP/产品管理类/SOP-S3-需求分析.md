# SOP-S3: 需求分析

> **版本**: v1.0
> **日期**: 2026-04-24
> **作者**: Tony Stark
> **状态**: 草稿

---

## 1. 概述

### 1.1 目标

理解业务需求，填充需求理解的 9 项信息

### 1.2 触发时机

- 收到新业务需求
- 产品经理提出新想法
- 用户反馈问题

### 1.3 输入

- 原始需求（文字描述、会议纪要、用户反馈等）

### 1.4 输出

- 需求理解报告（9项信息填充）
- 需求补充文档

---

## 2. 处理流程

### 步骤 1: 需求接收

**输入**：
- 原始需求描述
- 需求来源
- 需求类型

**操作**：
1. 记录需求来源
2. 初步分类（功能需求/非功能需求/技术需求）
3. 分配需求 ID：`REQ-{YYYYMMDD}-{序号}`

---

### 步骤 2: 需求理解

**Skill 调用**：`requirement-understanding`

**填充 9 项信息**：

| # | 信息项 | 说明 |
|:---:|:---|:---|
| 1 | 需求类型 | 功能/非功能/技术/运营 |
| 2 | 需求背景 | 为什么做 |
| 3 | 用户群体 | 谁会用 |
| 4 | 用户场景 | 怎么用 |
| 5 | 功能范围 | 做什么 |
| 6 | 非功能需求 | 性能/安全/可用性 |
| 7 | 验收标准 | 怎么算完成 |
| 8 | 优先级 | P0/P1/P2/P3 |
| 9 | 依赖关系 | 依赖什么 |

**输出**：`requirement-understanding` 输出结构化需求 JSON

---

### 步骤 3: 需求补充

**Skill 调用**：`requirement-supplement`

**补充内容**：

| 补充项 | 说明 |
|:---|:---|
| 用户场景 | 详细描述用户使用场景 |
| 功能边界 | 包含什么/不包含什么 |
| 验收标准 | 可量化、可验证的标准 |
| 异常情况 | 边界条件、错误处理 |

**输出**：`requirement-supplement` 输出补充后的需求文档

---

### 步骤 4: 需求确认

**操作**：
1. PM 审核需求理解报告
2. 确认 9 项信息填充完整
3. 确认需求补充内容
4. 签字确认

**输出**：需求确认签字

---

## 3. 验收检查清单

- [ ] 需求 ID 已分配
- [ ] 9 项信息已填充
- [ ] 用户场景已描述
- [ ] 功能边界已明确
- [ ] 验收标准可量化
- [ ] PM 已确认

---

## 4. 关联 Skill

| Skill | 用途 | 调用时机 |
|:---|:---|:---|
| `requirement-understanding` | 需求理解 | 步骤2 填充9项信息 |
| `requirement-supplement` | 需求补充 | 步骤3 补充细节 |

---

## 5. 需求 ID 规范

```
REQ-{YYYYMMDD}-{序号}

示例：
REQ-20260424-001  # 2026年4月24日第1个需求
REQ-20260424-002  # 2026年4月24日第2个需求
```
