**更新日期**: 2026-04-29

## 一、机制概述

### 1.1 走查定位

**走查目标**: 确保产品域内各层级文档符合模板要求、内容正确、不过期

**核心价值**:
- 文档结构规范性
- 内容准确性
- 更新时效性
- 与Neo4j图数据库一致性

### 1.2 核心理念

```
产品域 → Epic → 本地文档库 → Neo4j Feature
   ↓         ↓           ↓           ↓
  6个      22个       目录结构    图数据库
   ↓         ↓           ↓           ↓
 一致性检查 ← ← ← ← ← ← ← ← ← ← ← ← ←
```

## 二、文档审查三层模型

借鉴代码审查的3层模型，构建文档审查的三层体系：

```
┌─────────────────────────────────────────────────────────────┐
│                    文档审查三层模型                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  🐛 L1: AI Quick（自动化）                                  │
│  ├── Lint + 类型检查  → 格式规范、命名规范、结构完整性       │
│  ├── 模板匹配度       → 文档是否符合模板要求                  │
│  ├── 版本时效检查     → 是否长期未更新(>3个月)                │
│  └── 安全扫描         → 敏感信息检查(密码/密钥)              │
│                                                             │
│  🤖 L2: AI Deep（深度分析）                                   │
│  ├── 逻辑正确性       → 文档内容逻辑是否自洽                  │
│  ├── 完整性检查       → Epic/Feature/Story是否完整           │
│  ├── 跨文档一致性     → 多文档间描述是否一致                  │
│  └── 可追踪性         → 需求→设计→实现链路是否完整           │
│                                                             │
│  👤 L3: Human终审                                            │
│  ├── 架构决策         → 关键架构是否合理                      │
│  ├── 业务逻辑         → 业务流程是否正确                     │
│  ├── 可维护性         → 文档结构是否易于维护                  │
│  └── 决策确认         → 重大变更Human Review                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 L1: AI Quick（自动化检查）

**检查方式**: 脚本自动化执行，无需人工干预

| 检查项 | 检查内容 | 通过标准 | 异常处理 |
|:---|:---|:---|:---|
| **Lint格式检查** | Markdown语法、标题层级、表格格式 | 无语法错误 | 自动修复或告警 |
| **命名规范检查** | 文件命名是否符合 `YYYY-MM-DD-类型-标题-vX.Y.md` | 符合规范 | ⚠️重命名 |
| **结构完整性** | 5个标准子目录是否齐全 | 目录完整 | ⚠️缺失告警 |
| **模板一致性** | PRD/操作手册是否符合对应模板要求 | 符合模板 | ⚠️模板偏离告警 |
| **版本时效** | 文档最后更新时间 | ≤90天 | ⚠️需更新 |
| **敏感信息扫描** | 是否包含密码/密钥等敏感信息 | 无敏感信息 | 🔴删除+告警 |
| **多版本规范** | 同类型文档是否只保留最新版本 | 无历史堆积 | 自动归档 |

### 2.2 L2: AI Deep（深度分析）

**检查方式**: AI辅助分析，需结合Neo4j数据

**产品层级关系（四层结构）**：
```
Epic
└── Feature（功能域）
    └── Story（用户故事）← 归属关系，直接挂钩
         └── FP（功能包）← 多对多关系，一个Story可修改多个FP
```

| 检查项 | 检查内容 | 通过标准 | 异常处理 |
|:---|:---|:---|:---|
| **逻辑正确性** | 文档内容逻辑自洽性 | 无逻辑矛盾 | ⚠️需人工确认 |
| **层级完整性** | Epic→Feature→Story→FP四层关系是否正确 | 四层关系正确 | ⚠️补充缺失 |
| **Story归属准确性** | Story是否正确挂在对应Feature下 | Story正确归属Feature | ⚠️需修正 |
| **Story-FP关联** | Story是否关联了正确的FP（多对多） | Story至少关联1个FP | ⚠️需补充 |
| **FP定义完整性** | FP是否对应功能清单的功能点 | FP有明确功能点编号 | ⚠️需补充 |
| **Neo4j一致性** | 本地文档与图数据库数据是否一致 | 100%一致 | 同步修复 |
| **跨文档一致性** | PRD/技术方案/操作手册描述是否一致 | 描述一致 | ⚠️需对齐 |
| **系统定位准确性** | 系统上下游关系是否准确 | 上游明确，无下游流转说明 | ⚠️需确认 |
| **模块归属准确性** | Feature是否正确归属Epic | 所有Feature正确归属 | ⚠️需修正 |
| **功能清单同步** | 功能清单是否随Neo4j更新 | 功能清单包含Feature ID映射 | ⚠️需同步 |
| **需求追踪** | 业务需求→Feature→Story→FP链路是否完整 | 链路完整 | ⚠️补充追踪 |
| **Feature粒度** | 每个Epic下Feature数量是否在3-15范围 | 3≤F≤15 | 调整 |
| **模板内容一致性** | 文档章节结构是否与模板一致 | 章节完整 | ⚠️补充缺失章节 |
| **frontmatter完整性** | 文档是否包含neo4j/feishu/doc元数据 | frontmatter完整 | ⚠️补充缺失 |

### 2.3 L3: Human终审

**检查方式**: 人工Review，重大事项决策

| 检查项 | 检查内容 | 通过标准 | 异常处理 |
|:---|:---|:---|:---|
| **架构决策** | 技术架构设计是否合理 | 架构合理 | 讨论确认 |
| **业务逻辑** | 业务流程是否符合业务需求 | 流程正确 | 需求确认 |
| **可维护性** | 文档结构是否易于维护和扩展 | 结构清晰 | 结构调整 |
| **决策记录** | ADR/重大决策是否记录 | 有决策记录 | 补充ADR |

## 三、走查流程

### 3.1 标准走查步骤

```
① 确定走查产品域
       ↓
② L1 AI Quick（自动化）
   ├─ 格式检查
   ├─ 命名规范检查
   ├─ 结构完整性检查
   ├─ 模板一致性检查  ← 新增
   ├─ 版本时效检查
   └─ 敏感信息扫描
       ↓
③ L2 AI Deep（深度分析）
   ├─ 逻辑正确性分析
   ├─ 层级完整性检查
   ├─ Neo4j一致性比对
   ├─ 跨文档一致性检查
   ├─ 系统定位准确性检查
   ├─ 模块归属准确性检查
   ├─ 功能清单同步检查
   ├─ 模板内容一致性检查
   ├─ frontmatter完整性检查
   └─ 需求追踪链路验证
       ↓
④ L3 Human终审（必要时）
   ├─ 架构决策Review
   ├─ 业务逻辑确认
   └─ 可维护性评估
       ↓
⑤ 输出走查报告
       ↓
⑥ 问题修复 & 归档处理
```

### 3.2 三层审查决策流

```
文档提交
    ↓
L1 AI Quick ──通过──→ L2 AI Deep ──通过──→ L3 Human终审
    │                  │                    │
  失败/告警          失败/需确认          通过
    │                  │                    │
  自动修复           AI辅助修复           完成
    ↓                  ↓                    ↓
输出L1报告        输出L2报告            输出L3报告
```

## 四、Epic标准目录结构

每个Epic目录下必须包含：

```
Epic名称/
├── 业务需求入口/          # 原始需求文档 ✅必须
├── 需求拆解结果/          # Epic/Feature/FP/Story拆解 ✅必须
├── 产品PRD/               # 产品需求文档 ✅必须
├── 产品操作手册/          # 使用指南 ✅必须
├── 技术方案/              # 技术实现方案（可选）
└── archive/               # 历史版本归档目录 ✅当有历史版本时
```

## 五、文档版本管理规则

### 5.1 版本控制原则

| 文档类型 | 保留策略 | 归档要求 |
|:---|:---|:---:|
| **PRD文档** | 只保留最新版本(vX.Y) | 历史版本→archive/ |
| **Feature文档** | 只保留最新版本 | 历史版本→archive/ |
| **Story清单** | 只保留最新版本 | 历史版本→archive/ |
| **技术方案** | 只保留最新版本 | 历史版本→archive/ |
| **业务需求** | 可保留多个(原需求) | 标注日期 |
| **会议纪要** | 按时间归档 | 可保留多个 |

### 5.2 版本命名规范

```
最新版本: YYYY-MM-DD-类型-标题-vX.Y.md
归档版本: archive/YYYY-MM-DD-类型-标题-vX.Y归档.md
```

## 六、走查检查清单

### 6.1 L1 AI Quick 检查清单

| 检查项 | 标准 | 异常标记 |
|:---|:---|:---:|
| Markdown语法 | 无语法错误 | ⚠️语法错误 |
| 文件命名 | `YYYY-MM-DD-类型-标题-vX.Y.md` | ⚠️命名不规范 |
| 标准目录 | 5个标准子目录齐全 | ⚠️目录缺失 |
| **模板一致性** | PRD/操作手册符合模板 | ⚠️模板偏离 |
| 版本时效 | 最后更新≤90天 | ⚠️文档过期 |
| 敏感信息 | 无密码/密钥 | 🔴敏感信息 |
| 多版本 | 同类型只保留1个 | ⚠️需归档 |

### 6.2 L2 AI Deep 检查清单

**产品层级关系（四层结构）**：
- Epic → Feature → Story（归属关系）
- Story ↔ FP（多对多关系）

| 检查项 | 标准 | 异常标记 |
|:---|:---|:---:|
| 逻辑正确性 | 内容逻辑自洽 | ⚠️逻辑矛盾 |
| 层级完整性 | Epic→Feature→Story→FP四层关系正确 | ⚠️链路缺失 |
| **Story归属准确性** | Story正确挂在对应Feature下 | ⚠️归属错误 |
| **Story-FP关联** | Story至少关联1个FP | ⚠️未关联FP |
| **FP定义完整性** | FP对应功能清单功能点 | ⚠️FP定义缺失 |
| Neo4j一致性 | 本地=Neo4j | ⚠️数据不一致 |
| 跨文档一致 | PRD/技术方案/手册描述一致 | ⚠️描述不一致 |
| Feature粒度 | 3≤Feature数≤15 | ⚠️粒度异常 |
| **模板内容一致** | 文档章节结构与模板一致 | ⚠️章节缺失 |

### 6.3 L3 Human终审 检查清单

| 检查项 | 标准 | 异常标记 |
|:---|:---|:---:|
| 架构设计 | 架构合理且有文档记录 | ⚠️需Review |
| 业务流程 | 流程正确且符合需求 | ⚠️需确认 |
| 可维护性 | 结构清晰易于维护 | ⚠️需优化 |
| ADR | 重大决策已记录 | ⚠️需补充 |

#### Feature模板内容归属原则（v3.2新增）

| 要描述的内容 | 应该写入的章节 | 示例写法 |
|:---|:---|:---|
| 筛选器/控件默认值 | 功能清单(4.1) 的 FP 描述中 | "FP-001: 预算筛选器，支持业务类型多选(默认全选)" |
| 计算规则/判定逻辑 | 功能清单(4.1) 的 FP 描述中 | "FP-002: 健康度判定，实际剩余/预估剩余>1.1为超支" |
| 预警触发条件 | 验收标准(5) | "预警触发：实际剩余低于预估的X%时发送通知" |
| 数据表/数据来源 | 依赖关系(6) | "adm.ads_report_ws_prod_consuption_full: 预算数据" |
| 状态流转规则 | 功能清单(4.1) 或 用户流程(4.2) | 在 FP 描述或用户流程中描述 |

**⚠️ 避免创建独立章节**：筛选器说明、计算规则章、预警规则章、数据来源章等都是冗余章节，内容应归入上述章节。

### 附1.3 PRD模板必须章节

| 章节 | 必须 | 说明 |

## 附三、产品走查日志机制（v3.1新增）

### 附3.1 核心理念

```
目的：记录走查历史，避免重复检查已通过文档

已通过文档（内容未变更） → 跳过L1基础检查
需修复文档 → 跟踪修复进度
新文档/变更文档 → 完整检查
```

### 附3.2 日志文档结构

每个Epic目录下新增 `走查日志.md`：

```
Epic名称/
├── 业务需求入口/
├── 需求拆解结果/
├── 产品PRD/
├── 产品操作手册/
├── 技术方案/
└── 走查日志.md        ← 新增，记录该Epic的走查历史
```

### 附3.3 日志模板

路径: `产品管理项目/模板/10-产品走查日志.md`

| 章节 | 说明 |
|:---|:---|
| 走查历史 | 日期/人员/层级/结果 |
| 已通过文档 | 通过检查的文档列表，状态锁定 |
| 需修复文档 | 问题列表 + 修复状态 |
| 模板一致性检查 | PRD/操作手册章节检查记录 |

### 附3.4 检查跳过规则

| 条件 | 动作 |
|:---|:---|
| 文档在`已通过列表`中 | 跳过L1基础检查，直接L2深度检查 |
| 文档`内容有变更` | 重新完整检查 |
| 文档`新增` | 完整检查 |
| 文档`内容无变更`且`在已通过列表` | 仅验证状态，跳过L1 |

### 附3.5 走查流程更新

```
① 确定走查Epic
       ↓
② 检查走查日志
   ├─ 文档在已通过列表？ → 是 → 检查内容是否有变更
   │                            ├─ 无变更 → 跳过L1，直接L2
   │                            └─ 有变更 → 完整检查
   │
   └─ 文档不在列表？ → 完整检查
       ↓
③ 执行L1+L2+L3检查
       ↓
④ 更新走查日志
   ├─ 通过 → 加入已通过列表
   └─ 未通过 → 加入需修复列表
       ↓
⑤ 输出走查报告
```

### 附3.6 模板路径

```
产品管理项目/模板/
└── 10-产品走查日志.md    # 每个Epic的走查日志模板
```
