# Task Planning and Breakdown (本地定制版)

## Overview

将工作分解为小的、可验证的任务，带有明确的验收标准。好的任务拆分是可靠完成工作和产生一团乱码的区别。

## The Planning Process

### Step 1: 进入 Plan Mode

在写任何代码前，纯读模式：
- 阅读 spec 和相关代码
- 识别现有模式和约定
- 映射组件间依赖
- 记录风险和未知项

**规划阶段不写代码。** 输出是计划文档，不是实现。

### Step 2: 识别依赖图

```
数据库 schema
    │
    ├── API models/types
    │       │
    │       ├── API endpoints
    │       │       │
    │       │       └── Frontend API client
    │       │               │
    │       │               └── UI components
    │       │
    │       └── Validation logic
    │
    └── Seed data / migrations
```

实现顺序从依赖图底部开始：先建基础设施。

### Step 3: 垂直拆分

按功能路径构建，不是按层构建：

**❌ 不好（水平拆分）**：
```
Task 1: 构建整个数据库 schema
Task 2: 构建所有 API 端点
Task 3: 构建所有 UI 组件
Task 4: 连接一切
```

**✅ 好（垂直拆分）**：
```
Task 1: 用户可以创建账户（注册 schema + API + UI）
Task 2: 用户可以登录（认证 schema + API + UI）
Task 3: 用户可以创建任务（任务 schema + API + UI）
Task 4: 用户可以查看任务列表（查询 + API + UI 列表视图）
```

每个垂直切片交付可工作、可测试的功能。

### Step 4: 编写任务

```markdown
## Task N: [简短描述标题]

**描述**：一段话解释任务完成什么。

**验收标准**：
- [ ] 具体可测试条件
- [ ] 具体可测试条件

**验证**：
- [ ] 测试通过：`npm test -- --grep "feature-name"`
- [ ] 构建成功：`npm run build`
- [ ] 手动检查：[描述验证什么]

**依赖**：[依赖的任务号，或"无"]

**可能修改的文件**：
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**估算规模**：[小: 1-2 文件 | 中: 3-5 文件 | 大: 5+ 文件]
```

### Step 5: 排序和检查点

排序满足依赖的任务，确保：
1. 依赖已满足（先建基础设施）
2. 每个任务使系统处于可工作状态
3. 每 2-3 个任务有验证检查点
4. 高风险任务在前（快速失败）

添加明确检查点：

```markdown
## Checkpoint: Task 1-3 后
- [ ] 所有测试通过
- [ ] 应用构建无错误
- [ ] 核心用户流程端到端可用
- [ ] 与人工确认后继续
```

## 任务规模指南

| 规模 | 文件数 | 范围 | 示例 |
|------|--------|------|------|
| **XS** | 1 | 单个函数或配置变更 | 添加验证规则 |
| **S** | 1-2 | 一个组件或端点 | 添加新 API 端点 |
| **M** | 3-5 | 一个功能切片 | 用户注册流程 |
| **L** | 5-8 | 多组件功能 | 带过滤和分页的搜索 |
| **XL** | 8+ | **太大——进一步拆分** | — |

如果任务是 L 或更大，应进一步拆分。

**何时进一步拆分**：
- 需要多个专注会话（~2+ 小时 agent 工作）
- 无法用 3 个或更少要点描述验收标准
- 触及两个或更多独立子系统
- 任务标题中写"和"（这意味着是两个任务）

## 并行化机会

多个 agent 或会话可用时：

- **可安全并行**：独立功能切片、已有功能的测试、文档
- **必须顺序**：数据库迁移、共享状态变更、依赖链
- **需要协调**：共享 API 契约的功能（先定义契约，再并行）

## Common Rationalizations

| 借口 | 真相 |
|------|------|
| "做的时候再想" | 这是产生意大利面条代码的方式 |
| "任务很明显" | 还是要写下来。明确的任务暴露隐藏依赖和遗忘的边界情况 |
| "规划是开销" | 规划就是任务。没有计划的实现只是在打字 |

## Red Flags

- 没有书面任务列表就开始实现
- 任务说"实现功能"但没有验收标准
- 计划中没有验证步骤
- 所有任务都是 XL 规模
- 任务间无检查点
- 未考虑依赖顺序

## Verification

开始实现前确认：

- [ ] 每个任务有验收标准
- [ ] 每个任务有验证步骤
- [ ] 任务依赖已识别并正确排序
- [ ] 无任务涉及超过 ~5 个文件
- [ ] 主要阶段间有检查点
- [ ] 人工已审查并批准计划
