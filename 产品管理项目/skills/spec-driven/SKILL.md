# Spec-Driven Development (本地定制版)

## Overview

在写任何代码前，先写 PRD。Spec 是岩王帝君的契约——一旦制定，必须遵守。

PRD 涵盖：
- **目标**：这个需求要解决什么问题？
- **范围**：什么做，什么不做？
- **验收标准**：怎么算完成？（可测试的条件）
- **边界**：输入输出、约束条件

## 本地项目 PRD 模板

```markdown
# PRD: [功能名称]

## 背景
[为什么需要这个功能？解决什么问题？]

## 目标
- [ ] 目标 1
- [ ] 目标 2

## 范围

### 做
- [ ] 范围项 1
- [ ] 范围项 2

### 不做
- [ ] 超出范围项 1
- [ ] 超出范围项 2

## 验收标准

### 功能验收
- [ ] 标准 1
- [ ] 标准 2

### 非功能验收
- [ ] 性能：< 200ms 响应时间
- [ ] 安全：无 XSS、SQL 注入
- [ ] 可访问性：WCAG 2.1 AA

## 技术决策

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 状态管理 | Redux / Zustand / Context | ? | 待定 |

## 风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| API 尚未完成 | 高 | 隔离 API 层，使用 Mock |

## 本地项目约束

### 数据社区
- UI 组件库：Arco Design
- 禁止修改：`accompany.ts`、`calculation.ts`
- 路由需同步侧边栏菜单

### 产品管理系统
- 后端：Spring Boot + Neo4j
- 前端：Vue 3
- API：`/api/` 前缀

### Agent Dashboard
- 前端：React + TypeScript
- 后端：Express
```

## When to Use

- 启动新项目
- 新功能开发
- 重大变更
- agent 被要求做不明确的任务时

## The Process

### Step 1: Clarify（澄清）

在写 spec 前，先澄清：
- 需求是什么？要解决什么问题？
- 谁是用户？用户故事是什么？
- 成功标准是什么？
- 有什么约束？（技术、时间、资源）

### Step 2: Write PRD（写 PRD）

使用上面的模板，写完整 PRD。

### Step 3: Review PRD（审查 PRD）

- [ ] 目标清晰、可测量
- [ ] 范围明确（做什么 + 不做什么）
- [ ] 验收标准可测试
- [ ] 技术决策有理由支撑
- [ ] 风险已识别

### Step 4: Approve（批准）

**Checkpoint**：必须由派蒙或文博批准后才能进入开发。

### Step 5: Implement（实现）

按照 PRD 实现，变更必须同步更新 PRD。

## Common Rationalizations

| 借口 | 真相 |
|------|------|
| "需求很清晰，直接做" | 模糊需求导致返工，10 分钟 spec 节省 1 小时返工 |
| "我会边做边想" | 边做边想会产生意大利面条代码 |
| "Spec 写太详细会限制创意" | Spec 定义边界，不限制实现细节 |

## Red Flags

- 没有书面 PRD 就开始写代码
- PRD 验收标准无法测试
- 范围不清晰（"等"）
- 技术决策没有理由

## Verification

Spec 完成后：
- [ ] 有书面 PRD
- [ ] PRD 经过审查
- [ ] 得到人工批准（派蒙/文博）
- [ ] 技术决策有理由支撑
