## 第一章：项目全景设计

### 1.1 双项目架构

**项目关系定位**

产品管理系统 V4.0（工具层）管理和支撑 数字社区项目（产品层）等多个产品项目。

```
┌─────────────────────────────────────────────────────────────┐
│                    产品管理系统 V4.0                         │
│                   （工具层 - Tony Stark 负责）                 │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐         │
│  │需求拆解 │  │本体建模 │  │知识检索 │  │数据同步 │         │
│  │ Agent   │  │ Agent   │  │ Agent   │  │ Agent   │         │
│  └─────────┘  └─────────┘  └─────────┘  └─────────┘         │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │         产品知识图谱 (Neo4j)                        │   │
│  │  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐    │   │
│  │  │  Epic  │──│ Feature│──│ Story  │──│   FP   │    │   │
│  │  └────────┘  └────────┘  └────────┘  └────────┘    │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                            │
                            │ 管理 & 同步
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                    数字社区项目                              │
│              （产品层 - 实际开发的产品）                      │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐         │
│  │数字营销 │  │数据发现 │  │数据探索 │  │电销工作台│         │
│  │(PD-MKT) │  │(PD-DFD) │  │(PD-DEX) │  │(PD-COM) │         │
│  └─────────┘  └─────────┘  └─────────┘  └─────────┘         │
│                                                             │
│  技术栈: Vue 3 + TypeScript + Element Plus                  │
│  仓库: data_community (frontend/)                           │
└─────────────────────────────────────────────────────────────┘
```

**核心原则**：

| 原则 | 说明 |
|:---|:---|
| 工具层 vs 产品层 | 产品管理系统是工具层，服务多个产品项目 |
| 分工明确 | 数字社区是产品层，其中一个具体项目 |
| Tony Stark | 负责产品管理（需求、规划、协调） |
| 钟离 | 负责技术实现（代码、架构、数据库） |

### 1.2 五层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 0: 业务需求入口层                                        │
│  输入: 飞书消息、邮件、口头沟通、文档                           │
│  处理: 自然语言理解 → 结构化需求提取                            │
├─────────────────────────────────────────────────────────────────┤
│  Layer 1: AI 需求拆解层 ⭐                                       │
│  输入: 结构化需求                                               │
│  处理: LLM 智能拆解 → Epic/Feature/Story/FP                     │
├─────────────────────────────────────────────────────────────────┤
│  Layer 2: 本体论语义层 ⭐                                       │
│  输入: 拆解结果                                                 │
│  处理: 本体验证 → 语义对齐 → 冲突检测                           │
├─────────────────────────────────────────────────────────────────┤
│  Layer 3: 图与向量层 ⭐                                         │
│  存储: Neo4j (图) + Milvus/PGVector (向量)                      │
│  功能: 知识图谱 + 语义检索                                      │
├─────────────────────────────────────────────────────────────────┤
│  Layer 4: 数据与资源层                                          │
│  存储: 飞书多维表格、代码仓库、设计稿、PRD 文档                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 五阶段工作流程

| 阶段 | 说明 |
|:---:|:---|
| 阶段1 | 人工理解需求背景 |
| 阶段2 | 结构化分析输出 |
| 阶段3 | AI智能拆解 Epic/Feature/Story/FP |
| 阶段4 | 人工审核确认 |
| 阶段5 | 导出同步到Neo4j和飞书 |

详细流程参见：附录 B - 执行计划详细时间表

## 第二章：Subagent 拆分方案

### 2.1 上下文驱动拆分

**3 层 × 3 个 = 9 个 Subagent**

| 层级 | Subagent |
|:---|:---|
| 产品上下文层 | 需求理解、产品分析、PRD生成 |
| 技术上下文层 | 代码结构扫描、技术拆解、技术评估 |
| 执行上下文层 | 数据同步、状态跟踪、周报生成 |

详细规范参见：附录 E - Subagent 详细规范

### 2.2 与旧方案对比

| 维度 | 旧方案 | 新方案 | 改进 |
|:---|:---|:---|:---:|
| 拆分逻辑 | 按工作流程顺序 | 按「谁看的文档」 | ✅ 更清晰 |
| 上下文范围 | 单 Agent 混杂多层信息 | 每层 Agent 只看自己层 | ✅ 更简洁 |
| Token 效率 | 8,000+ tokens/请求 | 3,000 tokens/请求 | ✅ 节省 62% |
| 可复用性 | 低，与流程绑定 | 高，可独立使用 | ✅ 更灵活 |
| 测试难度 | 高，需要完整流程 | 低，可单独测试 | ✅ 更易测试 |
